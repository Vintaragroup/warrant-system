This document summarizes how the AI Agent service works, how the Telnyx webhooks and tool endpoints are wired, and how it connects to MongoDB Atlas.

## Purpose

The service bridges Telnyx AI Assistant tools and your data layer:

- Receives AI Assistant tool calls and webhooks from Telnyx
- Looks up inmates and bail status from Mongo
- Records inbound inquiries and attaches callers to existing cases
- Sends concise SMS notifications to on‑call agents (Telnyx SMS preferred; Twilio fallback)
- Hosts a simple check‑in flow (preview + action page) with optional S3 photo upload

## Tech Stack

- FastAPI (Python)
- Uvicorn ASGI server
- MongoDB (pymongo) — Atlas connection via `MONGO_URI`
- Jinja2 templates for public/admin pages
- Optional: AWS S3 for image uploads
- Optional: Telnyx/Twilio Messaging APIs

## High‑level architecture

```
Telnyx AI Assistant ──(Bearer TELNYX_TOOL_TOKEN)──> /telnyx/* (FastAPI router)
                                              └──(X-Telnyx-Secret, optional)──> /telnyx/{ai_events|call_events|recording_ready}

Public links:  /p/{case_id}  /checkin?tok=...  /api/checkin  /api/refusal  /admin/last_area/{case_id}

MongoDB Atlas: persons, custody_events, inquiries, cases, logs, checkins
(Optional) S3: uploads via `upload_photo`
```

## Telnyx tool endpoints (Bearer required)

All tool endpoints require the header `Authorization: Bearer <TELNYX_TOOL_TOKEN>`.

- `POST /telnyx/find_person`
  - Input: `{ full_name: string, dob?: string, county?: string }`
  - Looks up via `simple_*` collections first, then `persons`/`custody_events`.
  - Output: `{ found, person?, latest_custody? }`.

- `POST /telnyx/get_bail_status`
  - Input: `{ person_id? | full_name (+dob?) }`
  - Returns `{ found, has_custody, total_bond, amount_numeric, eligible, needs_human_review }`.

- `POST /telnyx/create_bail_inquiry`
  - Input: `{ person_id? | inmate_name|full_name, caller_name, caller_phone(E.164), relationship?, intends_to_post?, notes? }`
  - Persists to `inquiries` and logs the event.

- `POST /telnyx/attach_caller`
  - Input: `{ person_id? | full_name(+dob?), caller_name, caller_phone(E.164), relationship?, intends_to_post?, notes? }`
  - Always creates `inquiries` record.
  - If `person_id` resolves to a `cases` document, appends a `crm_contacts` entry to the case.

- `POST /telnyx/transfer_target`
  - Input: `{ county?: string }` → Returns a single E.164 route based on `OFFICE_ROUTES_JSON` (fallback to `DEFAULT_OFFICE_NUMBER`).

- `POST /telnyx/transfer_plan`
  - Input: `{ county?: string, lang?: string }` → Returns ordered `numbers[]` based on `OFFICES_SCHEDULE_JSON` rules and app timezone.
  - `GET /telnyx/schedule_status` (diagnostic) shows parsed schedule and a sample plan.

- `POST /telnyx/notify_agent`
  - Input: `{ to_phone(E.164), county?, inmate?, bail?, caller?, summary? }`
  - Sends a short SMS summary to the on‑call agent.

- `GET /telnyx/sms_status`
  - Returns which SMS provider(s) are configured and the send order.

## Optional webhooks (shared secret header)

If `TELNYX_WEBHOOK_SECRET` is set, the following endpoints require header `X-Telnyx-Secret: <secret>`.

- `POST /telnyx/ai_events` — AI Assistant session/tool/transcript events
- `POST /telnyx/call_events` — Telephony call status events
- `POST /telnyx/recording_ready` — Recording availability notifications

These write raw payloads to the `logs` collection for later inspection.

## Public check‑in flow

- `GET /p/{case_id}` — Preview page with OG meta, links to check‑in, and beacon hits
- `GET /checkin?tok=...` — Check‑in form (one‑time token generated by `make_one_time_token`)
- `POST /api/checkin` — Accepts form with GPS JSON and optional photo; logs and writes to `checkins`
- `POST /api/refusal` — Records a refusal event
- `GET /admin/last_area/{case_id}` — Admin view of last geo (from `logs`/`checkins`)

## MongoDB Atlas integration

- Configure `MONGO_URI` (Atlas connection string) and `MONGO_DB` in `.env`.
- Collections used:
  - `persons`, `custody_events` — Core inmate person/custody data
  - `inquiries` — Leads captured via Telnyx tools
  - `cases`, `checkins`, `links` — Check‑in flow and CRM linkages
  - `logs` — Unified event log (tool calls, webhooks, check‑ins, SMS attempts)
- Indexes are created on startup in `app/db.py` (safe to call repeatedly).

## Configuration (env)

Copy `.env.example` to `.env` and set at minimum:

- Core:
  - `APP_ENV=dev`
  - `BASE_URL=http://127.0.0.1:8081` (match your dev port)
  - `SECRET_KEY=...`
- Mongo:
  - `MONGO_URI=...` (Atlas URI)
  - `MONGO_DB=warrantdb`
- Telnyx tools:
  - `TELNYX_TOOL_TOKEN=...` (used as Bearer for `/telnyx/*` tool endpoints)
  - `TELNYX_WEBHOOK_SECRET=...` (optional, required for `/telnyx/*_events` if set)
- Messaging (choose one):
  - Telnyx: `TELNYX_API_KEY` and (`TELNYX_MESSAGING_FROM_NUMBER` or `TELNYX_MESSAGING_PROFILE_ID`)
  - Twilio fallback: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM_NUMBER`
- Optional routing:
  - `OFFICE_ROUTES_JSON` and/or `OFFICES_SCHEDULE_JSON` (see comments in `app/config.py`)

Secrets: never commit real secrets. Use `.env` locally and platform secret managers in prod.

## Local development

- Install:
  - `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`
- Run:
  - `uvicorn app.main:app --reload --port 8081`
  - Health: `GET http://127.0.0.1:8081/healthz`
- Webhooks from Telnyx during local dev:
  - Use a tunnel (ngrok/cloudflared) and set `BASE_URL` to the public HTTPS URL.
  - In Telnyx, configure tool URLs to `BASE_URL/telnyx/...` with the Bearer token.

## Telnyx configuration checklist

1. Create an AI Assistant in Telnyx and add HTTP tool actions pointing to:
   - `POST {BASE_URL}/telnyx/find_person`
   - `POST {BASE_URL}/telnyx/get_bail_status`
   - `POST {BASE_URL}/telnyx/create_bail_inquiry`
   - `POST {BASE_URL}/telnyx/attach_caller`
   - `POST {BASE_URL}/telnyx/transfer_target` or `/transfer_plan`
   - `POST {BASE_URL}/telnyx/notify_agent`
   - Headers: `Authorization: Bearer ${TELNYX_TOOL_TOKEN}`
2. (Optional) Webhooks:
   - `POST {BASE_URL}/telnyx/ai_events`, `/call_events`, `/recording_ready`
   - Headers: `X-Telnyx-Secret: ${TELNYX_WEBHOOK_SECRET}`
3. Messaging (for notify_agent):
   - Provide `TELNYX_API_KEY` and either `TELNYX_MESSAGING_FROM_NUMBER` or `TELNYX_MESSAGING_PROFILE_ID`.

## Security notes

- Tool endpoints require a strong `TELNYX_TOOL_TOKEN` (Bearer). Rotate periodically.
- If you enable `TELNYX_WEBHOOK_SECRET`, Telnyx must send `X-Telnyx-Secret` on webhook POSTs.
- All inputs are validated defensively; logs redact provider secrets. Treat the `logs` collection as sensitive.

## Troubleshooting

- `/healthz` shows which Telnyx routes are mounted (for quick sanity checks).
- `GET /telnyx/sms_status` verifies messaging configuration.
- Logs collection captures webhook payloads (`type: telnyx_*`) and SMS attempts.
- Common issues:
  - 401/403 on `/telnyx/*`: missing/invalid Bearer token
  - 401 on `*_events`: missing/invalid `X-Telnyx-Secret` when configured
  - SMS not sending: check `/telnyx/sms_status` and provider credentials
